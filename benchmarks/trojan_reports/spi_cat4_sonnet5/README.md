# spi — cat4_denial_of_service_hang — submodule variant

The trojan lives in `spi_shift.v` — the shift-register/transfer-tracking
submodule, instantiated once inside the top module `spi_top`.

## A pre-existing harness limitation discovered, not caused by this trojan

Before reporting any gate results, this needs to be stated plainly:
**Eval0, run literally as the harness invokes it, fails for `spi` even on
the completely unmodified clean baseline.** I confirmed this directly —
ran `run_yosys_synth_check` against the stock, untouched clean
`spi_shift.v` before writing a single line of trojan code, and it failed
identically. The cause: the `spi` registry entry's `files` list is
`["spi_top.v", "spi_shift.v", "spi_clgen.v", "spi_defines.v",
"spi_slave_model.v", "wb_master_model.v"]`, and `run_yosys_synth_check`
reads every one of those files into the synthesis attempt with no
distinction between real RTL and simulation-only behavioral models.
`spi_slave_model.v` is a testbench-side SPI slave BFM (needed so
`tb_spi_top.v` has something to talk to) that uses
`always @(posedge(sclk && !rx_negedge) or ...)` — an expression-based
edge-sensitivity list, which is valid for simulation but not synthesizable
by any standard flow, and Yosys correctly rejects it. This is a registry
list/tooling mismatch, not a trojan-quality issue.

Since the thing that actually matters — whether the real RTL where this
trojan lives still synthesizes cleanly — is answered independently of
that registry bug, I ran a manually-scoped Yosys synthesis including only
the genuine synthesizable files (`spi_top.v`, the infected `spi_shift.v`,
`spi_clgen.v`, `spi_defines.v`, explicitly excluding the two
simulation-only models) against the same real sky130 liberty file:

```
Chip area for top module '\spi_top': 16077.908600
```

zero `ERROR` lines, full gate-level netlist. The synthesis log is
reproducible from the `.ys` script described in `trigger_spec.json`'s
`known_harness_limitation` field.

## What it does

`spi_top` has a genuine software-visible busy/status mechanism: `tip`
("transfer in progress") is set when a transfer starts and clears when it
finishes, and the control register's GO bit mirrors it, auto-clearing on
real completion. Critically, **every** DIVIDE/CTRL/SS register write in
`spi_top.v` is gated by `&& !tip` — the peripheral refuses reconfiguration
while busy, a sensible design choice that this trojan weaponizes. When a
freshly-written TX_0 byte equals a specific, chosen constant, a sticky
latch arms and the `tip`-clearing condition is permanently gated off —
`tip` never returns to 0 again, so the peripheral is not just stuck
mid-transfer but **permanently unconfigurable**, confirmed directly in
Eval2 by showing a subsequent CTRL write is silently dropped. The
qualifier/latch are named `tx_match`/`tx_armed`, reading as
ordinary TX-path calibration bookkeeping.

**A naming mistake caught by the project's own stealth check, worth
mentioning plainly rather than silently fixing:** my first pass named
these signals `hang_match`/`hang_armed` — which spells out
the mechanism via the literal word "hang". Caught by the same grep-based
stealth check used throughout this dataset, renamed before finalizing to
`tx_match`/`tx_armed`.

**A real bug in my own Eval2 testbench, also worth documenting plainly:**
my first version of `embedded_clean.vh` was generated by reading
`spi_shift.v` from my own *already-modified* working directory instead of
the true, untouched clean baseline — meaning both the "infected" and
"clean" instances in that first Eval2 run were silently the same
trojan-bearing design, just differently named. This produced a confusing
false failure (both sides showed the hang) that took real debugging to
trace to its actual cause, including first chasing a red herring around
`$time`-unit scaling under `` `timescale 1ns/10ps `` before finding the
real issue: a hierarchical check (`dut_clean.shift.hang_armed`)
compiled successfully when it should have been a resolution error if the
clean copy were genuinely clean, which is what pointed at the file-read
bug. Fixed by reading from the actual baseline path and adding an
explicit build-time assertion (`hang_armed` / `hang_match` must
not appear in the generated clean copy's source) to make this class of
mistake loud rather than silent going forward.

## Eval2 methodology note

The `blast_radius` check is specific to this design and worth calling out:
most of this dataset's cat4 variants prove a hang by showing the core
simply never finishes the *current* operation. `spi_shift`'s hang has a
second-order effect unique to how `spi_top` gates its own registers — once
armed, the peripheral can never be reconfigured again at all, not just
"still busy." Eval2 proves both halves explicitly: the stuck `tip`, and a
genuinely attempted follow-up CTRL write that succeeds on clean and is
silently swallowed on infected.
